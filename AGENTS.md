# AGENTS.md

Проект: MongoDB TUI Viewer (C# / .NET 10, Terminal.Gui 2.5).

## Архитектура
- Onion: Domain → Application → Infrastructure → TUI.
- Domain не зависит ни от чего, кроме System.* и MongoDB.Bson.
- Application зависит только от Domain.
- Infrastructure реализует интерфейсы Application.
- TUI знает только Application; Infrastructure подключается в Program.cs через DI.

## Принципы
- SOLID, SRP, KISS, DRY. Никаких абстракций "на будущее".
- Класс < 300 строк, метод < 40 строк.
- Всё через конструкторный DI. Никаких `new` сервисов внутри сервисов.
- Async всюду, где есть I/O. `CancellationToken` — всегда последний параметр.
- Никаких `static` кроме чистых утилит без состояния.

## Стиль C#
- `nullable enable`, `TreatWarningsAsErrors=true`.
- `using`-директивы — перед file-scoped `namespace`.
- File-scoped namespaces.
- Точка входа (`Program.cs`) — top-level statements, без `class Program` и `Main`.
- `var` — когда тип очевиден из правой части.
- Records для DTO/иммутабельных моделей.
- `sealed` для классов по умолчанию.
- Никаких регионов.

## Нейминг
- Интерфейсы: `IName`.
- Приватные поля: `_camelCase`.
- Async-методы: суффикс `Async`.
- Тесты: файл `XxxTests.cs`, класс `XxxTests`.

## Тесты
- Фреймворки: xUnit + FakeItEasy + AwesomeAssertions.
- Именование тестов: `Should{Not|Throw}_{ExpectedOutcome}_When{Scenario}()`.
- AAA-разделение пустыми строками.
- Один `Act` на тест.
- Интеграционные тесты — в `MongoTui.IntegrationTests` с Testcontainers.
- Покрытие: Domain ≥ 90%, Application ≥ 80%, Infrastructure — по критичным местам.

## Логирование
- Serilog, только в файл `~/.mongotui/logs/app-.log`.
- Никогда не логировать connection string, пароли, содержимое документов.
- Уровни: Debug — детали, Info — действия пользователя, Warning — recoverable, Error — баги.

## Локализация

- Логи и исключения — по-английски.

## Definition of Done
- Собирается без warnings.
- Все тесты зелёные (`dotnet test`).
- Новая функциональность покрыта тестами.
- Нет закомментированного кода и `TODO` без issue-ссылки.

## Do / Don't
- DO: маленькие PR, явные типы в публичных API, DI, тесты рядом с фичей.
- DON'T: `Thread.Sleep`, `.Result`/`.Wait()` в async-коде, `Console.WriteLine` (ломает TUI), `dynamic`, обход интерфейсов.

## Асинхронные запросы и UI в Terminal.Gui 2.5

### Причина зависаний вложенных диалогов
- В 2.5.0 `TimedEvents.RunTimers()` удерживает блокировку очереди во время callback.
  Вложенный `application.Run(dialog)`, открытый из таймера/async-продолжения,
  удерживает эту блокировку до закрытия окна. Фоновый `application.Invoke` добавляет
  таймер и блокируется; `SynchronizationContext.Post` также использует `Invoke`.
  Запрос уже выполнен, но UI остаётся на «Сохранение…» или показывает старый список.
- Нельзя считать, что обычный `await` надёжно вернёт исполнение в UI во вложенном окне.
  Рабочий шаблон: I/O без захвата контекста, затем явная передача результата в главный цикл.

### Выполнение запросов
- Перед запросом прочитать поля и выбранные роли на UI-потоке, создать снимок входных
  данных, показать прогресс и заблокировать повторный запуск операции.
- В Application/Infrastructure использовать `ConfigureAwait(false)` во всей цепочке
  ожиданий I/O. Если метод только возвращает чужой `Task`, вернуть его напрямую.
  Один `ConfigureAwait(false)` во внешнем обработчике не исправляет захват контекста
  внутри вызываемого сервиса или gateway.
- В TUI ожидать запрос через `ConfigureAwait(false)`. После такого `await` нельзя
  читать или изменять контролы напрямую: продолжение может выполняться в пуле потоков.
- Не оборачивать асинхронный MongoDB/SSH/file I/O в `Task.Run` ради обхода контекста.
  `Task.Run` уместен для отдельной тяжёлой CPU-работы со снимком данных.
- Передавать `CancellationToken` до gateway. Для запросов, которые могут пережить
  закрытие окна, предусмотреть отмену и проверку актуальности результата; результат
  старого запроса не должен перезаписывать новый или обращаться к disposed-контролам.

### Передача изменений в UI
- Использовать переданный через конструктор экземпляр `IApplication`.
  Не создавать второй экземпляр приложения и не смешивать instance API со static API.
- Для передачи результата из фонового потока использовать проектный
  `ApplicationUiExtensions.InvokeAsync` и ожидать его с `ConfigureAwait(false)`.
  На UI-потоке он исполняет действие сразу; из фонового потока подписывается на
  `IApplication.Iteration`, обходя блокировку таймеров. Он отписывается до исполнения
  действия, поэтому открытие вложенного диалога не вызовет повторный запуск callback.
  Возвращённый `Task` завершается после UI-действия и передаёт его исключения вызывающему.
- Нативный `Invoke` не устраняет описанную блокировку. Не заменять проектный helper
  на `Invoke`, фоновый `AddTimeout` или `SynchronizationContext.Post` без регрессионного
  теста вложенного окна. Не менять UI напрямую из фонового потока ради обхода блокировки.
- Все изменения `Text`, `Enabled`, `Visible`, источника списка, выделения, схемы цветов,
  открытие диалогов и `RequestStop` после I/O выполнять внутри такого UI-действия.
- В `Invoke`/`InvokeAsync` передавать синхронный `Action`. Не передавать `async`-лямбду:
  она превратится в `async void`, и завершение/исключения операции перестанут отслеживаться.
- Применять связанные изменения одним UI-действием: данные списка, выделение, доступность
  кнопок и статус. После изменения собственной отрисовки вызвать `SetNeedsDraw()`.
  Это помечает кадр для перерисовки, но не заменяет передачу в UI-поток.
- Обработать успех, ошибку и отмену. Снять прогресс и восстановить кнопки до
  `RequestStop(dialog)`: после закрытия вложенного цикла позднее UI-действие может
  уже не исполниться. Готовые пароль/URI показывать после успешного сохранения,
  до необязательной перезагрузки списка, которая сама может завершиться ошибкой.
- `InvokeAsync` требует работающего главного цикла. До запуска цикла на его будущем
  UI-потоке допустима синхронная настройка контролов; нельзя ждать поставленное в ещё
  неработающий цикл действие из фонового потока.

Пример завершения запроса в обработчике TUI:

```csharp
var request = ReadFields(); // UI-поток, до первого await
SetBusy(true);
Exception? error = null;
try
{
    await _service.SaveAsync(request, cancellationToken).ConfigureAwait(false);
}
catch (Exception exception)
{
    error = exception;
}

await _application.InvokeAsync(() =>
{
    SetBusy(false);
    if (error is not null) ShowError(error);
    else _application.RequestStop(this);
}).ConfigureAwait(false);
```

### Обязательная проверка асинхронного UI
- Одних fake gateway с уже завершённым `Task` недостаточно: они скрывают захват контекста.
- В регрессионном тесте запустить реальный цикл Terminal.Gui с ANSI driver,
  родительским окном и вложенным `Run(dialog)` из callback главного цикла.
- Завершать `TaskCompletionSource` с `RunContinuationsAsynchronously` из фонового
  продолжения, например после `Task.Delay(...).ConfigureAwait(false)`, а не из UI-таймера.
- Без дополнительных нажатий проверить экран, снятие прогресса, восстановление кнопок,
  закрытие формы при успехе и сообщение при ошибке. Ограничить тест страховочным таймером.
- Проверять en/ru и цепочку создания/смены пароля до окна с копированием данных.
  Примеры: `UserFormDialogSaveTests`, `UserManagementDialogRenderingTests`.
- В unit-тестах без реального цикла с fake `IApplication` настроить `MainThreadId`
  на текущий поток; в тестах фоновой передачи действительно запускать главный цикл.
